## Token and time interpretation

For the fast A failures with 400–670k `local_tokens`, the job usage records closely match that count in **cumulative prompt tokens**, not generated output: `rx-01` 539,830 prompt / 3,004 completion; `tf-02` 409,679 / 1,133; `tf-03` 539,195 / 2,299; `tf-05` 668,683 / 2,072. Their prompt-cache counters are also large (386k–598k cached). The observed failure pattern is many repeated test/inspection turns (23–40 turns; `rx-01` has 40 calls/turns and many searches into vendored React code), so the gross counter is consistent with accumulated conversation/tool history. It is **not** evidence of a 400–670k generated answer or one enormous output. The cache counters mean it would be inaccurate to describe all of these as fully re-prefilled tokens. Available records do not break prompt tokens down per turn or by tool output, so the respective contributions of growing prompt history, tool output, and uncached prefill cannot be quantified further.

B's long runs correlate with thinking on every turn and increased generated reasoning: on `tf-03`, completion rose from 2,299 (A) to 26,869 (B) at 40 turns; on `tf-05`, 2,072 to 30,267 despite B using only 17 turns. `HarnessKnobs.swift` configures shipped thinking as all turns, medium, with an 8,192-token thinking turn allowance; `AgentLoop.swift` allows up to 40 turns and the delegated profile allows 900 seconds / 60,000 generated tokens. Thus B's cap is supported by measured time/turn/completion evidence, not merely a slow test command. Several B records were externally cancelled around 817–860 model seconds, while ledger wall times land at roughly 900 seconds.

## Ranked harness changes

1. **Progress gate after a failed verification (prompt + loop control).** After the first failing test run, require a short structured diagnosis (`failing assertion → source symbol → intended change`) and then an edit before another full-suite run. If files are unchanged and the same failure signature recurs twice, issue one focused nudge and stop or finish as blocked. Keep exact-call detection, and add normalized command/signature detection for equivalent repeated test/filter commands. **Addresses:** rb-03 A/B, tf-02 A/B, tf-03 A/B, tf-04 B, tf-05 A/B; also rx-01 A's repeated investigation. **Expected cost/risk:** low runtime cost; moderate risk of stopping a legitimate investigation whose first edit needs more diagnosis, mitigated by one recovery nudge.
2. **Make thinking conditional, bounded recovery rather than all-turn.** Keep thinking off for normal inspect/edit/test turns. Trigger one medium-thinking recovery turn only after two unchanged failed verifications, repeated failure signatures, or an explicit unresolved diagnosis; then return to normal mode. **Addresses:** B timeouts across rb-03, tf-02, tf-03, tf-04, tf-05. **Expected cost/risk:** likely large latency/token reduction based on B completion counts; moderate risk that some genuinely difficult first-turn reasoning gets less help. This trigger is supported by these failures' repeated unchanged tests; it is not a guarantee of better correctness.
3. **Preserve structured test status and compact failure evidence.** Detect test commands even when piped, retain the underlying process exit code (pipefail or structured command status), and return a compact failure digest with failing test names, expected/actual, and source locations. Preserve the raw full output only on request. **Addresses:** all test-fix tasks; especially rx-01 where pipeline commands show exit 0 although Bun reports 1 failure, and repeated test reruns on tf-02/03/05. **Expected cost/risk:** low-to-moderate implementation cost; risk of misclassifying custom scripts, so expose both pipeline and underlying command status.
4. **Add semantic stall detection over files and failing signatures.** Track whether a successful edit occurred since the last test, whether the same failing-test digest recurs, and whether commands are semantically equivalent despite different pipes/filters. On a stall, state the unchanged evidence and require a new source target or a finish decision. **Addresses:** rb-03 A/B; rx-01 A; tf-02 A/B; tf-03 A/B; tf-05 A/B. **Expected cost/risk:** moderate implementation cost; false positives possible when repeated tests are intentionally used to validate a fix, so only trigger when no successful edit occurred.
5. **Use task-class-specific budget warnings and spend caps, not a blanket larger timeout.** At 25% and 50% of turns/time, report remaining budget and ask for the smallest missing source change; for thinking turns, enforce a lower per-turn reasoning cap and reserve a modest completion budget. Do not raise the 900 s limit as a first response: these logs show turns spent repeating diagnosis rather than making edits. **Addresses:** B all-turn exhaustion and A 40-turn loops. **Expected cost/risk:** low runtime cost and likely lower wasted inference; risk of premature termination for unusually broad tasks, mitigated by progress-based thresholds.

### Limits that harness changes cannot fully remove

The reference work is small and the tests expose the intended behavior, but several failures still require the model to translate assertion evidence into correct code semantics: e.g. Ruby block arguments/stability and truncation boundaries in `rb-03`, custom `IsBoolFlag` behavior in `tf-03`, and the optional-time API in `tf-05`. Better prompts, output shape, and stall controls can reduce wasted turns and make these obligations obvious; they cannot guarantee a correct implementation. That residual is a model capability/training question. The records do not support declaring the Go toolchain or environment as the root cause in these cases.
