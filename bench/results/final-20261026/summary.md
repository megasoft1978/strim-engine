# Final all-engine HTTP benchmark: Qwen3.8-27B (2026-10-26/27)

Qwen3.8-27B served alone over HTTP by each engine, same prompts and workloads (scoreboard W1-W5, 8-turn synthetic agent replay, sampled decode), thinking off (`chat_template_kwargs.enable_thinking=false`; Ollama has no such field, so its Modelfile template hardcodes the empty think block). Apple M5 Max, 64 GB, macOS 27.0.1. Every pass ran under `lockf -k /tmp/strim-bench.lock` with the engine as the only GPU job; load snapshots (uptime, loadavg, top CPU) are in each `<engine>/pass<N>/steps.log`, per-rep `uptime`/`loadavg` in the scoreboard `raw.jsonl`. Raw JSON per run: `<engine>/pass<N>/scoreboard/raw.jsonl`, `replay/raw.jsonl`, `sampled.jsonl`, `server.log`, `meta.json`. Drivers: `bench/final_all.sh`, `bench/final_run.py`, `bench/final_replay.py`, `bench/final_sampled.py`, `bench/final_aggregate.py` (this file is generated by the last one from `notes.json` + raw files). Strim is `strim serve` at default settings (prefix cache budget default 12288 MB, `--no-auth` only to let the unauthenticated bench client in). Scoreboard cell = median over reps of the per-rep median; `(n)` = reps. Bold = best in row. Weights: MLX 4-bit (`models/qwen38-4bit`) for the MLX engines, Q4_K_M GGUF (`models/gguf/Qwen3.8-27B-Q4_K_M.gguf`, 17.4 GB) for llama.cpp and Ollama. Strim and rapid-mlx also run the MTP head (`models/qwen38-mtp-4bit`); mlx-lm, tensorfold (default drafts as shipped), omlx, mlx-vlm, llama.cpp and Ollama are as launched below.

## Caveats

- Quant difference: MLX engines run the MLX 4-bit checkpoint (Strim and rapid-mlx with the MTP head); llama.cpp and Ollama run the bartowski Q4_K_M GGUF of the same base model. Rates are not weight-identical; quality of the two quants is not compared here.
- Speculative decoding is part of the product: Strim and rapid-mlx use the MTP head; tensorfold ships drafts but its server log shows one round per token and accepted=0/0 in this launch, and its decode (about 30 tok/s) matches the non-speculative engines, so drafts were effectively inactive here; mlx-lm, omlx, mlx-vlm, llama.cpp and Ollama decode one token at a time. The decode lead is MTP plus kernels together, not kernels alone.
- Prefill is NOT a Strim win. Cold TTFT at 4K/16K/32K is within about 1-5% across Strim, rapid-mlx, tensorfold and mlx-vlm; Strim is 1-5% slower than rapid-mlx and mlx-vlm at every size (4K 4.18 s vs 4.15 / 4.04; 16K 17.4 vs 17.0 / 16.7; 32K 37.5 vs 36.3 / 35.7) and mlx-vlm has the lowest median in all three rows. W1 TTFT (short prompts) is best on tensorfold (0.088 s), Strim second (0.111 s).
- Agent replay prefill: rapid-mlx leads Strim (sum of per-turn TTFT 49.7 s vs 54.5 s, cached fraction at T8 87.2% vs 85.3%); the supplemental tensorfold --context 65536 launch (50.1 s) and mlx-lm (54.4 s) are in the same band, and Strim's 54.5 s is only about 9% above the best. Over turns 1-6 (the part every engine completed, llama.cpp stops at its 32768 slot) the order is rapid-mlx 35.1 s, tensorfold 35.4 s, Strim 37.8 s, mlx-lm 39.6 s. Strim's cache restores at 1024-token node granularity (T8 cached 34816 of 40840). Replay sends recorded assistant turns, so Strim's token ledger / hot-session reuse does not apply. Replay TTFT includes the first decode step. mlx-vlm has no cross-turn prefix reuse (0% cached, 192.9 s). Ollama's T1 TTFT (6.1 s) is slower than the others partly from its larger prompt (4130 tokens).
- Concurrency: aggregate throughput is flat at about 11-13 tok/s for strim, rapid-mlx, mlx-lm and mlx-vlm in W4 (distinct cold 4K prompts, 64 tokens each); the aggregate is dominated by 4K prefill time, so engines are within noise (mlx-vlm highest at 13.5 for c4). Per-request decode in W4 is NOT comparable across engines: Strim prefills serially and its per-request clock for later requests includes waiting, so Strim's per-request decode (18.7 c2 / 6.8 c4) is far below rapid-mlx (29.5 / 24.5), mlx-lm (27.5 / 22.8) and ollama; rapid-mlx batches decode. Strim wins only W4 c4 TTFT (10.7 s), because its first-request TTFT is not delayed by batched prefill.
- Shared prefix (W5, 4 concurrent requests sharing a 16K prefix): Strim gets 4 of 16 request rows with a cache hit (1024 cached tokens each) because the four requests arrive together and prefill serially without sharing in-flight work. tensorfold (98.5K cached tokens) and Ollama (143K) win aggregate (6.34 and 5.74 vs 3.33 tok/s) and TTFT (35.9 and 34.6 s vs 46.6 s); llama.cpp (98K cached) wins aggregate (4.52) but is slower than Strim on TTFT (50.7 s). rapid-mlx, mlx-lm and mlx-vlm are slower than Strim on TTFT (70-76 s); rapid-mlx does not report cached_tokens for these rows (unknown). This is a real Strim gap on this workload, not just a cache-granularity effect.
- ignore_eos: rapid-mlx, mlx-lm, mlx-vlm, omlx and Ollama sometimes ended before the requested token count (`short` rows; replay turns 3-8 for rapid-mlx, mlx-vlm and omlx; mlx-lm replay turns 3+; Ollama 6 W-rows). Short rows are dropped from decode and aggregate medians (missing, not slow) but kept for TTFT. Replay decode tok/s is therefore not tabulated; use replay TTFT/prefill only.
- Replay measurement: the replay client (`bench/final_replay.py`, a shim over the unmodified `bench/agent_replay.py`) sends enable_thinking=false and counts the first content, reasoning or tool_calls delta as the first output. mlx-lm, tensorfold and Ollama parse tool calls into `tool_calls` deltas, so unpatched `agent_replay.py` reported `no content chunk` for them (pass1 raw rows kept). Where a server emits a tool call only after buffering it, its TTFT includes up to 48 decode steps (about 1 s). Prompt token counts differ slightly by engine template: Ollama's hand-written ChatML template renders 40 more tokens than the MLX/llama.cpp jinja path (49 vs 89 for W1 prompts, 4093 vs 4130 at replay T1), and has no Qwen tools block.
- Ollama: imported from the GGUF with a Modelfile (num_ctx 65536, OLLAMA_NUM_PARALLEL=2 to match llama.cpp's -np 2, OLLAMA_FLASH_ATTENTION=1), isolated OLLAMA_MODELS dir, own port 11435. Its lower decode than llama-server on the same GGUF is measured, not explained. Cache hit counts are inflated by a ~40-token shared template prefix on every request (W1 48/48 rows, W3 9/9 rows with 42 cached tokens each); only W5 and replay show real reuse.
- tensorfold cache logging: cached_tokens=3 on most rows (a BOS-level hit) including cold W3 rows; negligible (3 of 4107 tokens) but those rows are not strictly zero-cache. llama.cpp W1 shows 10/48 rows with small hits (prompt-cache slot reuse of a shared template prefix). rapid-mlx omits cached_tokens on most rows (unknown) and reports hits on some W1/W2 repeats.
- Memory: oMLX peak RSS 24 GB and a 56 GB Metal ceiling; its guard aborted W5 (see skipped). llama.cpp RSS 36.6 GB and Ollama 35 GB include the 8 GB prompt cache and mapped weights (RSS of the server tree via the scoreboard sampler; not comparable across runtimes).
- Load: shared workstation, otherwise idle apart from the desktop (loadavg 1.4-3 at rep starts, a few peaks to 8-10 that include the benchmark's own work; see the load column and steps.log). A 30-minute real-client soak (bench/soak) held the lock until about 07:03 and the first pass started right after it. The Strim/rapid-mlx ABAB reduces but does not remove drift; CVs in the scoreboard summaries are mostly under 2% for decode.
- Strim W3 decode at 16K (48.8) and 32K (48.5) is flat within the run-to-run CV (up to 6.6% at 32K); do not read a trend into it.
- Sampled decode (temp 1.0, top_p 0.95, top_k 20, seed 1234, 256 tokens, n=3 per pass): Strim and rapid-mlx are equal within noise (47.6 vs 47.4). Honoring of top_p/top_k/seed by each server is not verified. omlx's pass1 sampled rows (no_usage after the unload) are excluded; pass2 rows are valid.
- Results are for one model on one machine at one date; the engines' versions move quickly.

## Run order

ABAB for Strim vs rapid-mlx: strim pass1, rapid-mlx pass1, strim pass2, rapid-mlx pass2 (2 scoreboard reps and 2 replay reps per pass, so n=4 each; warm-up request discarded per pass; server restarted per pass). Then once each (3 scoreboard reps, 3 replay reps, 3 sampled): mlx-lm, tensorfold, omlx, mlx-vlm, llama.cpp, Ollama. Re-runs after the chain, same lock and launch lines: omlx pass2 (replay + sampled only; pass1 replay/sampled got HTTP 500 after omlx's memory guard unloaded the model during W5), mlx-lm / tensorfold / Ollama pass2 (replay only, with the replay client counting reasoning or tool_calls deltas as the first output; pass1 replay for those three had `no content chunk` turns), tensorfold-ctx64k pass1 (supplemental, W3 + replay only). Not ABAB for the other engines.
