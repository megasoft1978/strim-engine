What the data supports, and what it does not

Strim against rapid-mlx, mlx-vlm, mlx-lm and oMLX on Qwen3.8-27B 4-bit, one machine. Every claim below is computed from the cells in Results; losses are listed next to the wins.

  • Decode

    24-50% faster decode

    than rapid-mlx, the closest rival; 1.8-2.3x the speed of mlx-vlm, 1.9-2.5x the speed of mlx-lm and 1.7-2.2x the speed of oMLX, at 4K to 32K context. At 4K: Strim 75.34 vs rapid-mlx 50.12 vs mlx-vlm 32.69 vs mlx-lm 30.11 vs oMLX 33.53 tok/s.

    Engines differ in speculative decoding (MTP) and prefix caching; see the table of rivals above. Details

  • Four agents, one 16K prefix

    2.8-2.9x faster aggregate

    Four clients on one 16K prefix, aggregate tok/s. Median first token: Strim 20.29 s vs rapid-mlx 73.53 s vs mlx-vlm 70.48 s vs mlx-lm 73.4 s.

    Engines without a cross-request prefix cache cannot share the prefix in this setup. Details

  • Median first token under concurrency

    29-56% lower, 4 to 8 concurrent

    Against each rival, over 512-token, agent-style and 4K prompts.

    Some rivals report first tokens batch-synchronously, so their median is a weaker number. Details

  • Agent replay

    48.93 s 8-turn replay

    Summed prefill. Verdict against rapid-mlx (49.13 s): TIE; mlx-vlm (192.5 s): WIN; mlx-lm (55.02 s): WIN; oMLX (64.84 s): WIN.

    Engines without a cross-request prefix cache re-prefill every turn. Details

Where Strim is not faster

  • cold prefill is 2-4% behind it at 4K, 16K and 32K; aggregate throughput at 4 to 8 concurrent requests trails the best rival by more than 2% in 3 of 6 cells (2-4%); p95 first-token latency is more than 2% worse in 1 of 6 cells (6%).
  • No "fastest overall". 4 rivals, one model, one machine, thinking off. No head-to-head against llama.cpp, Ollama or LM Studio exists, so none is claimed.

Final head-to-head: Strim vs rapid-mlx, mlx-vlm, mlx-lm and oMLX

Qwen3.8-27B 4-bit served alone over HTTP by each engine, one engine on the GPU at a time, thinking off, greedy decoding, on one Apple M5 Max with 64 GB. 2 passes (pass 1 in the order Strim, rapid-mlx, mlx-vlm, mlx-lm, oMLX; pass 2 reversed), one rep per pass, so each value is the median of two runs, which is their mean. The largest swap growth in any session was 0 MB. Strim is build ee9f9d8; rapid-mlx ran as --no-telemetry serve models/qwen38-4bit --port 8651 --max-num-seqs 4 --speculative-config {mtp,qwen38-mtp-4bit} (MTP: yes (--speculative-config mtp, qwen38-mtp-4bit); prefix cache: yes, default on). mlx-vlm ran as --model models/qwen38-4bit --port 8651 (server defaults) (MTP: no; prefix cache: no cross-request reuse (0% cached in replay)). mlx-lm ran as --model models/qwen38-4bit --port 8654 --decode-concurrency 4 --prompt-concurrency 4 (MTP: no (no speculative decoding); prefix cache: yes, default in-memory LRU prompt cache). oMLX ran as serve --model-dir <scratch>/models (symlink to models/qwen38-4bit) --port 8653, HOME=<scratch>/home, defaults otherwise (memory-guard balanced, max-concurrent-requests 8) (MTP: no (MTP needs oMLX's own checkpoint; stock weights have no MTP head); prefix cache: yes, default paged SSD prefix cache under the scratch HOME (fresh per session, so no cross-session hits)). Verdict: WIN / LOSS when the ratio is outside a 2% band, otherwise TIE. Raw files, launch lines and the full per-rival tables: summary.md.

Strim decodes 24-50% faster than rapid-mlx, the closest rival; 1.8-2.3x the speed of mlx-vlm, 1.9-2.5x the speed of mlx-lm and 1.7-2.2x the speed of oMLX, at 4K to 32K context. rapid-mlx also uses MTP, so the gap to it is the engine, not the speculative head. mlx-vlm, mlx-lm and oMLX have no MTP, so their gap includes it.

Cold prefill (tok/s): within the 2% band of the best rival at none, 2-4% behind it at 4K, 16K and 32K. A tie is not a win.

Strim has the lowest median first-token latency at 4 to 8 concurrent requests, 29-56% lower than each rival. Caveat: rival p50 and p95 are nearly identical (their requests report first tokens batch-synchronously), so their p50 is a weaker number than Strim's per-request TTFT.

Strim is more than 2% behind the best rival in 3 of these six cells, by 2-4%. Batched decode narrows the gap but the remaining cost is the quantized matmul at 4 to 8 rows (below).

Strim's p95 is more than 2% worse than the best rival in 1 of these six cells, by 6%. The same staggering that gives a low median pushes the last request out.

With a shared 16K prefix Strim is 2.8-2.9x faster than each rival in aggregate throughput.

How it works

Decoding a 27B dense model is limited by memory bandwidth: every token streams the whole weight set. The gains come from more tokens per weight read, avoiding repeated work, and not wasting time between kernels.

MTP speculative decoding

The Qwen3.8 checkpoint ships a small multi-token-prediction head. Strim loads it (models/qwen38-mtp-4bit), drafts tokens with it and verifies them in one pass of the full model. Rejected drafts are rolled back exactly: the attention cache is sliced and per-token linear-attention (GDN) states are restored. Depth adapts (2-4 tokens). A 48k frequency-ranked draft vocabulary keeps the head cheap; verification uses the full vocabulary, so a missing token costs a rejected draft, never a wrong output. For sampled decoding the accept/residual/bonus rule keeps the output distribution unchanged.

Exact, chunk-aligned prefix cache

A trie over 1,024-token chunks holds KV, GDN state, conv state and the MTP head state per node, with an LRU byte budget. Prefill always runs in aligned chunks of that size whether or not the cache is used, so a hit restores exactly the state a miss would have computed. The token ledger records the exact ids the model produced, so resent histories reuse the model's own tokens and keep hitting the cache.

Blocked GDN prefill kernel

Linear-attention layers need a sequential recurrence. A blocked Metal kernel stages 48-token blocks in threadgroup memory and keeps state in registers. It was ported from rapid-mlx (Apache-2.0, itself adapted from oMLX) and is credited in NOTICE. At 4K it measured 825-846 tok/s before and 915 tok/s after at light load (878 at heavier load). The reduction order differs from the serial kernel, which is the source of the near-tie differences in Quality.

Batched decode kernels

Concurrent requests decode in lockstep through one batched forward pass. Batch-dimension GDN decode and conv Metal kernels (one dispatch for all sequences, per-row arithmetic identical to the single-stream kernel) cut the B=4 step from 49.5 to 42.3 ms against a single-stream floor of 34 ms. Served aggregate throughput went from 57.4 to 63.3 tok/s at c=4 and from 66.2 to 73.1 at c=8 in that sweep.

Those sweep numbers were taken under machine load and are already included in the build used for the head-to-head; they are not additional gains. The remaining c=4 gap is the quantized matmul at 4 to 8 rows. MTP inside the batch was measured and rejected (upper bound 1.09x before draft cost). See PLAN-CONCURRENCY.

Admission control

Every request takes a slot before the engine is touched. Interactive requests go first; background work (x-strim-priority: background, delegated jobs) is capped one slot below the total and re-queues between agent turns while interactive work is active, never mid-token. The default total is 8 slots (an admission cap, not the engine batch size). The engine also admits by memory and refuses requests that would not fit. Waiters are bounded and have a deadline. See ADMISSION.md.

Sandboxed harness

Delegated jobs run the local model as a coding agent in an isolated git worktree under sandbox-exec (no network, no credential reads, scrubbed environment), with contained file tools and a harness-run verify command. See Agents and Security.

Tried, measured, rejected

  • MTP inside the batch. Verify cost grows steeply with batch size: at 1K context 34.0 ms/pass for one token vs 120.3 ms/pass for three tokens each across four sequences. Upper-bound speedup over plain batching on prose 1.25× at B=2 and 0.99× at B=4, before draft and rollback costs. No-go. BATCH-MTP.
  • A custom 4-bit prefill GEMM. 4-bit matmul already runs at 0.90-0.98 of dense bf16 and dense GEMM plateaus at 62-63 TF/s; the optimistic end-to-end bound is +5-8%, below the plan's gate. No-go. PREFILL-SPIKE.
  • Batched prefill. B=4 at 4K ran at 0.95× the serial speed. Not adopted. BATCH-PREFILL.

Quality and exactness

The claim is narrow and has two parts.

  • Exact where it says so. A prefix-cache hit equals a miss bitwise (final-position logits and greedy tokens), within one fixed chunking policy: prefill always runs in aligned chunks, so cached and uncached runs follow the same arithmetic. That policy itself differs from a one-shot prefill (it costs 0.6% at 4K).
  • Not bitwise where it does not. Batched decode, the blocked GDN prefill kernel, speculative decoding and the cache cuts can change near-tie tokens (bf16 logits that tie within rounding; one flipped token changes every later one). Measured: greedy output over 8 fixed prompts and 64 tokens, Strim against itself across passes 8/8 identical, against rapid-mlx 7/8, against mlx-vlm 6/8. The batch kernels raised agreement with each prompt's own single-stream run from 6/8 to 8/8 at 96 tokens.

Multi-step agent quality has been checked on the corpora described in Agents (a real-client soak with toy tasks, a small real-client delegation run, and a Swift and Go task corpus of 17 tasks), not on a broad benchmark. What is not validated is listed under Limits.

Parity gates against Hugging Face

  • Tokenizer. Byte-level BPE checked against the HF tokenizer on encode, decode (including special tokens) and every chunking of streamed decode. Fixture tokenizer_parity.json, frozen; test TokenizerParityTests (skipped when the weights are absent).
  • Chat template. The native Qwen3.8 renderer (tool calls, reasoning, generation prompts) against HF-rendered text. Fixture template_parity.json.
  • Prompt ids. Template then tokenizer, including incremental multi-turn sessions through the ledger, equals HF ids. Fixture prompt_parity.json.
  • Special-token injection. User text (messages, reasoning, tool results, tool names, arguments, schemas) is tokenized as plain text, so a user cannot smuggle control strings into the prompt. Fixture prompt_adversarial.json.

Prefix cache gate

The checkprefix gate compares a cold run against hits on the final-position logit hash and 16 greedy tokens, and checks a cold store against the no-store reference, a second hit (no aliasing), a short prompt hitting a longer stored prefix, a forked tail, eviction under a tiny budget and an unrelated prompt missing cleanly. With MTP it also compares head KV, seed hidden state, logits and 64 speculative tokens. Logs: 4K, 8K, MTP. A hot session continued for 20 tokens equals a cold re-prefill (IDENTICAL over 20 tokens).

Security posture

Strim is a local, single-user server. It is not designed to be exposed to a network, and it does not defend against another process running as the same macOS user.

Design

  • Loopback only, with Host and Origin checks (DNS-rebinding and cross-site defence) and a refusal of cross-site fetches.
  • Bearer token by default (~/.strim/token, mode 0600, constant-time comparison), plus a separate control token for the menu-bar app. --no-auth opens only the API side for loopback development.
  • The local model is untrusted. Its shell runs under sandbox-exec (no network, writes only to the job worktree, no reads of credential directories), file tools are contained to the job workspace, jobs run in an isolated worktree, and a patch is applied only after an explicit approval carrying the SHA-256 of the exact bytes reviewed.

Reviewed and fixed (2026-10-28)

Three reviews: the server HTTP surface, every process launch and model-influenced code path, and release hygiene (secrets, personal data, licenses, supply chain).

  • Server surface: 14 findings, no critical and 1 high (an integer overflow trap from a client-controlled token count). 6 are fixed and one more partly: token-count clamping and saturating admission math, connection cap and head, body and idle deadlines, bounded request pipelining, a bounded response store, a waiter cap and queue deadline, a job-queue cap, and a minimal unauthenticated /health.
  • Process launches: 5 findings fixed: credential directories refused as job working directories, sandbox reads of shared temp areas denied, paid benchmark arms without a shell tool, the MCP token passed by environment reference instead of written to a file, and an opt-in for the unsandboxed legacy scripts.
  • Release hygiene: personal paths and a hostname scrubbed from committed results, token files ignored by git, license notices completed.

Residual risk, stated plainly

  • Any project under a non-denied home directory is allowed as a job working directory by default.
  • Paid benchmark arms must let the client read its own login file; file tools are denied it by permission rule, not by the sandbox.
  • No per-route body limit (one cap for all routes); no wall-clock limit on a running generation (output length is bounded instead); one API token means one priority class.
  • Token-store hardening against symlink races and permissive MCP token defaults are documented but not reworked (same-user only).
  • The reviews were read-only: no live server test, no fuzzing of the tokenizer or template parsers, and some sandbox fixes were not executed under sandbox-exec. The low and info items of the process-launch review were not addressed.

Report a vulnerability through GitHub private vulnerability reporting (the repository's Security tab); see SECURITY.md. Reviews: server, process launches, release hygiene.

Limitations

  • One model, one quantization, one machine class (64 GB Apple Silicon), one user. All measurements come from a single M5 Max.
  • Two passes with one rep each. Treat differences of a few percent as noise; gaps of a few percent sit at the edge of the 2% tie band.
  • Not faster: cold prefill is 2-4% behind it at 4K, 16K and 32K; aggregate throughput at 4 to 8 concurrent requests trails the best rival by more than 2% in 3 of 6 cells (2-4%); p95 first-token latency is more than 2% worse in 1 of 6 cells (6%).
  • Only the build named in the run summary at the top was benchmarked; later commits were not.
  • The prefix cache is in memory only. Speculative decoding and batching can differ from greedy at bf16 near-ties.
  • Not yet validated: live soak on the current build and harness, the paid agent-benchmark pilot, token savings from delegation, multi-step quality of batched decode and the cache cuts, other Mac memory tiers (see Agents and Scope).
  • The shipped StrimApp is a menu-bar shell over an older service and does not drive strim serve.
