# MTP head tuning plan — 2026-10-30

## Decision and evidence limits

Instrument and establish exactness first, then fine-tune the existing one-layer head against **the same 4-bit Strim target**, using its own continuations and cached hidden states. Start with a small offline experiment on the Mac; use one rented GPU and a separate training repository if the custom trainer is too slow. There is no measured gain for this head. A **0 to +5 percentage-point aggregate acceptance** planning range, with +5 to +10 points an optimistic stretch on low-acceptance agent text, is a hypothesis, not a published estimate or guaranteed speedup. Negative results are possible. Acceptance points, relative acceptance length, and throughput are different quantities. [GRIFFIN](https://arxiv.org/abs/2502.11018) reports over 8% relative acceptance-length improvement on different models/architecture; [domain draft training](https://arxiv.org/abs/2503.07807) demonstrates domain mismatch and distillation, but does not establish this head's gain. Local L16 sees acceptance vary approximately five points with numerics and depth, so paired, sufficiently large experiments matter.

**Exactness is a gate, not an assumption.** Greedy mathematical verification compares target argmax, but target kernels can produce different numerical results at different shapes. L16 reports pre-existing depth-dependent greedy differences and batch parity mismatches. Fix or constrain those paths before saying outputs are bit-identical. For sampled decoding, the current one-hot rejection sampler preserves the target **distribution**, not necessarily the same seeded token sequence across different heads or against plain sampling. Exact sampled bytes require an explicitly equivalent coupling or disabling speculation; statistical equivalence is a separate, weaker test. Never relax verification to boost acceptance.

## Current implementation

`Sources/StrimCore/MTP.swift`: one causal full-attention transformer block with its own KV cache, residual attention and MLP. At position i it pairs final-normalized target hidden h[i] with target embedding of token[i+1], separately RMS-normalizes them, concatenates 5120+5120 features, applies `fc`, block, and head norm; shared **target** `language_model.lm_head` predicts token[i+2]. The embedding and output projection are both from target, but they are not tied to each other (`tie_word_embeddings=false`). During multi-step drafting, the post-head-normalized hidden and predicted token are fed back; accepted positions are replayed with verified target hiddens. `Weights.swift` may use a tokenizer-hash-checked truncated draft vocabulary, which can itself limit acceptance; record its fingerprint and compare full-vocab control.

Read-only installed metadata identifies `mlx-community/Qwen3.8-27B-MTP-4bit`, revision `b643c01b6d3b094e325edb6ebd832e16c486c575`: config `qwen3_5_mtp`, one MTP layer, hidden 5120, MLP 17408, vocabulary 248320, 4-bit affine group 64. `model.safetensors` is 238,934,137 bytes, with indexed `fc`, norms, attention and MLP weights/scales/biases; no embedding or lm_head in head index. Config's `block_size: 3` is metadata, not three layers or a guaranteed runtime depth. Directory also contains tokenizer/config/template and pull manifest. No tensor values were read. See `Sources/StrimCore/Weights.swift` and `QuantConfig.swift` for per-tensor quantization handling.

`SpecStream.swift` starts adaptive decoding at depth 3 (constructor default 2; `EngineCore` configuration defaults 2), usually limits policy to 3, permits explicit fixed depth and configurable max. A round drafts k, increments `stats.drafts` by k, runs target on pending+drafts, accepts the **longest prefix** matching target argmax in greedy mode, rolls back the rejected suffix, emits accepted prefix plus target token, and reseeds. In sampling, acceptance is probabilistic under filtered target distribution (`SpecSampling.swift`). `SpecStats.acceptRate = acceptedDrafts/drafts`; proposed suffix positions after a rejection remain in the denominator. `EngineCore.swift` computes request delta `usage.mtpAccept` and passes, and `StrimOpenAIServer.swift` logs it; `/metrics` currently returns JSON engine/server resource counts, not acceptance. Counters can be updated immediately after `accepted` resolves, alongside `stats.acceptedDrafts`, without an extra GPU read.

Measured baselines are contextual, not interchangeable. `docs/SWIFT-PERF.md` (Oct 25) has natural prompt, depth 1/2/3: 55%/46%/36%; one code prompt depth 2: 85%, exact for 79 tokens. `docs/BATCH-MTP-2026-10-26.md` uses ~51% prose and 94% code in an optimistic verify-only analysis; general in-batch MTP was no-go for B>=3 then. `bench/results/speed-w2-L16-20261028/summary.md` fixed-d4 traces report survival P(prefix≥i), i=1..4, agent .76/.52/.33/.22, versus 4K .91/.78/.63/.51; four real agent prompts and three runs, with noisy shared machine. This implies agent mean accepted drafts 1.83/round at d4 and aggregate 45.75% if all rounds have four drafts. L16 also notes batch path has separate depth rules. Re-measure current revision, configuration, vocabulary and concurrency before use as a release baseline.

## Research and transfer

* [DeepSeek-V3](https://arxiv.org/abs/2412.19437) jointly trains MTP using sequential shifted tokens, shared embeddings/output and cross-entropy. Qwen's installed one-layer layout is similar in spirit; do not assume its original training recipe is published. [Medusa](https://proceedings.mlr.press/v235/cai24b.html) trains additional heads and uses target-generated self-distillation when original training data are unavailable. Our target is intentionally the deployed quantized verifier, so its numerical behavior is the teacher.
* [EAGLE-3](https://arxiv.org/abs/2503.01840) predicts tokens using multi-layer features and unrolls during training, reporting up to 6.5x in its own setting. [HASS](https://github.com/HArmonizedSS/HASS) aligns training and inference contexts; [GRIFFIN](https://arxiv.org/abs/2502.11018) addresses mismatch from generated drafts and masks misaligned tokens, reporting >8% relative acceptance-length and >7% speedup on its setup. These are architecture/experiment results, not expected MTP percentage-point gains. Unroll the existing MTP as deployed rather than replacing it with EAGLE or importing its multi-layer input contract.
* [Post-training MTP](https://arxiv.org/abs/2610.00888) reports ~2.5 billion generated tokens and plain CE on a frozen Qwen3-8B with three heads; this is a from-scratch research result, not a minimum for adapting a pretrained 27B head. Its relaxed verification permits distribution drift and is out of scope. [Domain draft training](https://arxiv.org/abs/2503.07807) examines teacher distillation under different data access; results depend on target, dataset and method. No reliable general rule for tokens or GPU-hours for this specific head was found.
* [SpecForge](https://github.com/sgl-project/SpecForge/blob/main/docs/sections/basic_usage/training.md) documents online/offline MTP and EAGLE3 training, including offline features. Verify the pinned release's exact Qwen3.8 architecture, tensor names, feature layout and loss before selecting it; support for MTP does **not** establish drop-in compatibility with Strim's MLX weights or stateful recurrence. Its SGLang export is not Strim format. A custom adapter and parity test are likely.
* [MLX Swift LM](https://github.com/ml-explore/mlx-swift-lm/blob/main/skills/mlx-swift-lm/references/training.md) documents LoRA training; MLX provides autodiff and optimizers. Neither establishes a ready-made trainer for this custom stateful quantized MTP. Implement a small separate head trainer with differentiable attention/cache and frozen embedding/lm_head, or use Python MLX outside this repo. On a 64 GB Mac offline head-only training is plausible, not measured: 239 MB quantized head corresponds very roughly to ~0.4B weights; BF16 parameters ~0.8 GB, gradients ~0.8–1.6 GB, FP32 Adam moments ~3.2 GB, possible FP32 master ~1.6 GB, plus frozen embedding/lm_head (up to ~5.1 GB BF16 together), activations, vocabulary logits, framework buffers and OS. Full BF16 logits alone are ~0.50 GB per 1,000 positions; use microbatches/chunking. Offline training need not load the 27B target; concurrent serving/training or long contexts may exceed usable unified memory. Measure peak memory on a tiny batch before committing.
* Budget estimate only: 1–10 million unique generated training tokens and 1–3 passes as a pilot, then 10–100 million if held-out improvement scales; do not equate cached samples with the 2.5B-token paper. Reserve 10–50 GPU-hours for a single 48–80 GB rented GPU **after data extraction**, with a possible 2–10x miss depending on full-vocab projection, sequence length, I/O and unroll; not a benchmark. First time 1,000 steps and extrapolate before renting more. Mac hours are unknown. Generation time is separate and likely substantial.
* [Qwen/Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) and the [installed community MTP](https://huggingface.co/mlx-community/Qwen3.8-27B-MTP-4bit) model cards state Apache-2.0, which permits modification and distribution subject to license, notices, attribution and marking changes. Verify exact source revisions and any bundled tokenizer/data licenses and include applicable LICENSE/NOTICE; training-data rights and privacy are separate. Do not infer terms from other Qwen variants.

## Data and dump

Source eligible prompts from `/tmp/px1/run`, `/tmp/ev1/run2` agentbench/evolve job events and `bench/results/*/raw`, plus consented representative chat. Preserve tool schemas, role boundaries, tool results, code edits, test output and chat template. `Sources/StrimJobs/Interfaces.swift` explicitly says mirrored events omit text deltas; some run trees contain ledgers and transient scratch files, so verify actual event paths and reconstructability before claiming transcripts exist. Do not ingest credentials, control tokens, arbitrary verify/home files, or generated caches. Redact secrets and sensitive data before export; provenance, authorization, retention and deduplication are required. Split by project/task family and conversation before generating continuations, keeping near-duplicates, repeated runs and shared source snippets together; reserve unseen projects and chat for final test. Labels apply to emitted token spans: structured tool-call JSON, code, prose, and unknown/mixed; use tokenizer byte offsets and role/parser metadata, never infer labels from the prompt alone. Report unknown and use one deterministic boundary precedence.

Generate continuations with the frozen production 4-bit target without MTP for teacher trajectories; store the full prompt and preceding context, exact token IDs, target-normalized final hidden at each consumed position, next greedy target ID and optional teacher distributions, masks, template/constraint and sampling metadata, EOS, offsets, reset boundaries and hashes (model, quant, tokenizer, template, code, weights, vocabulary). Token alignment: h[i] + embed(x[i+1]) predicts target x[i+2]; preserve explicit position mappings and loss masks so prompt/padding and document boundaries never leak. Capture rolling sequences with enough preceding head context for the real head KV/window; do not train isolated shuffled vectors. Generate on-policy greedy and a controlled mix of deployment sampling trajectories; use target-derived labels at the same prefixes. For multi-step drafts, unroll the trained head using its own outputs and query matching teacher prefix distributions; offline teacher-forced hiddens alone cannot supply correct targets once a draft diverges. Initially mask later loss after divergence, or separately collect verifier states for reachable draft prefixes; document which objective is used.

Proposed Swift CLI (future only): `strim mtpdump --model <dir> --prompts <jsonl> --out <dir> --max-new-tokens N --seed N --dtype bf16 --shard-tokens N [--teacher hard|topk|full] [--head-window N]`. JSONL prompt records carry ID, messages/template or exact IDs, constraints, content span metadata and split; output versioned manifest plus bounded safetensors shards of tokens, hiddens, masks, offsets and optionally teacher logits. Atomic create-only shards, checksums, resumable completed-shard manifest, local permissions, explicit error on fingerprint mismatch; never serialize KV as if it were reusable across incompatible models. Dry-run reports counts and storage. No service, implicit upload or access to port 8203. The offline replay must reproduce target IDs and normalized hidden alignment at short and long contexts against normal Strim before data generation.

Per 1M positions, BF16 hiddens = 1,000,000 × 5120 × 2 = **10.24 GB decimal** (9.54 GiB), plus ~4 MB each for int32 token/label IDs, masks and metadata; embeddings are looked up, not stored. Full 248,320-vocab BF16 logits = **496.64 GB decimal** per million positions, FP32 993.28 GB. Optional top-128 IDs+FP16 scores ~0.77 GB plus normalization/tail metadata; top-k alone is not exact full KL, and omitted tail must be accounted for or described as an approximation. Compression, storage for long context overlaps, validation and multiple layers add overhead. Shard and stream; no need to materialize 1M × vocabulary in RAM.

## Training, conversion and evaluation

1. **Mac first:** separate Swift/MLX trainer, or separate Python/MLX repository if faster to develop. Freeze target embedding and lm_head, train dequantized BF16 head initialized from installed 4-bit head. First reproduce its forward and cache outputs at fixed inputs to tolerance, then use fixed seeds and gradient checks. Keep trainable head FP16/BF16 or FP32 and quantize only at export; compare quantization-aware training later if export erases gains. Quantized target lm_head must match Strim; do not silently replace it with BF16 teacher.
2. **Single GPU fallback:** separate PyTorch/SpecForge-based trainer with imported Strim features and a validated MTP architecture, 48–80 GB preferred; no target model needed during offline head updates, though matching quantized output projection and embedding are needed. Offline features and prompt privacy determine whether remote training is permissible. Compatibility is a proof-of-concept gate, not an assumed CLI.
3. Baseline teacher-forced hard CE on target next-token argmax, then ablate forward KL `KL(P_target || P_draft)` at T=1 using full target distributions or accurately normalized tail, and mixed CE/KL. Full KL can capture uncertainty, but greedy agreement and sampled acceptance are the selection metrics, not loss alone. Mask non-output/padding and invalid contexts; preserve constraints. Evaluate 1–4 step unroll with deployed normalized-hidden feedback and shared cache, weighting depths 1–3 and recording depth 4. Log hard and KL separately; compare one-step-only baseline. Optimize AdamW, starting LR 1e-5 for full-head tuning (sweep 3e-6, 1e-5, 3e-5), warmup 3%, cosine decay, clip 1.0, effective 8k–32k supervised tokens/step, 500–3,000 steps initially; early stop on validation acceptance, not training loss. These are proposed hyperparameters, not measured optima. Track unique tokens and total token-updates separately.

Export an optional new head directory, preserving required tensor names, shapes, norms, metadata and tokenizer fingerprint. Requantize linears with MLX affine 4-bit/group 64 and correct per-tensor scales/biases, index and config; preserve any intended mixed precision explicitly rather than assuming all tensors are quantized. Manifest binds base model/quantization, tokenizer, training and head hashes, exporter version and license. Do not overwrite the original. Check loader key coverage, shapes, forward logits, cache/replay parity before and after conversion, and quantized-versus-unquantized acceptance. Publish only licensed head weights, never private traces.

Evaluate paired baseline and candidate on frozen held-out tasks at fixed depth 1–4 and production adaptive policy, full and production truncated vocabulary, by context length and content type; include hard tokens, generated outputs, resets and constraints. Report proposed, reached and accepted counts per position, prefix survival, conditional acceptance, accepted tokens/round, confidence intervals clustered by task/conversation, plus quantization loss. Then measure production end-to-end c=1/4/8, rotated paired repetitions, warm/cold prefix states, decode tok/s, TTFT, aggregate throughput, latency distribution, memory and actual MTP activation; c>=4 may use a different batch route or no MTP, so report coverage and do not attribute unrelated speed changes to the head. Resolve existing batch parity and shape-related greedy divergences; compare all output token IDs and UTF-8 bytes to no-MTP and baseline at each concurrency, masking/constraint settings, prompt and depth. Sampled runs require distribution tests and a separate explicit same-seed bit-parity gate; if the product promises same bytes, no rollout until a coupling or no-spec fallback passes. No numerical tolerance for claimed bit identity.

Ship as an optional head download with fingerprint compatibility checks and rollback first. Make default only if the exactness gates pass, paired held-out agent aggregate acceptance improves at least 3 percentage points with a 95% task-cluster interval above zero, no content category loses >2 points, and c=1 decode improves >=3% with no >2% regression in c=4/8 throughput or p95 latency under repeatable load; increase sample size if intervals overlap thresholds. These are proposed product gates, not paper claims. Refit depth policy only in a separate measured change.

## Instrumentation: first implementation slices

1. **Counters.** In `Sources/StrimCore/QwenModel.swift` extend `SpecStats` with per-position integer arrays; in `Sources/StrimCore/SpecStream.swift` update once per completed round from already materialized `roundDepth` and `accepted`: for each i≤depth increment proposed; if accepted≥i increment accepted-prefix; if accepted≥i−1 increment reached; conditional numerator is accepted-prefix. Proposals after first rejection count as proposed but not reached. Zero-depth, output-budget truncation, cancellation, constraints, sampled path, and fixed/adaptive depth must have explicit tests. Snapshot deltas across requests so reused sessions do not double count. Wire monotonic engine-lifetime totals through `Sources/StrimEngine/EngineCore.swift` and `EngineAPI.swift`, export bounded positional arrays under `engine.mtp` in the existing JSON `/metrics` in `Sources/StrimServer/StrimOpenAIServer.swift`; no prompt IDs or unbounded labels. Include resets/process lifetime and thread-safe snapshot semantics. Instrument actual batch path separately if it does not use `SpecStream`; show unsupported/zero coverage rather than claiming all traffic is captured. Add focused core/engine/server tests under `Tests/StrimCoreTests`, `Tests/StrimEngineTests`, `Tests/StrimServerTests` as applicable.
2. **Replay CLI.** Add `Sources/StrimCLI/Cmd_MTPStats.swift` and dispatch/help in `Sources/StrimCLI/main.swift`. `strim mtpstats --model <dir> --head <dir> --prompts <jsonl> [--depth 1,2,3,4|adaptive] [--max-tokens N] [--output <json>]` runs offline in-process with fresh caches and no server; emit counts/rates and uncertainty by position/content type, model/tokenizer/head/vocab/constraint fingerprints, seed/config, and unknown labels. For each output token map its span to tool JSON/code/prose; a round's position is classified by the proposed token's corresponding output span, with rejection and boundaries specified, and aggregate counters remain independent of labels. Include no-data handling, deterministic replay and tests for accounting/content labels in CLI tests. Compare fixed-depth counters with trace logs and preserve parity.
3. **Dump contract and correctness.** Add `Sources/StrimCLI/Cmd_MTPDump.swift`, CLI dispatch, and a narrowly scoped target hidden capture path in `Sources/StrimCore/QwenModel.swift`/`SpecStream.swift` as needed; define versioned shard/manifest types in a new `Sources/StrimCore/MTPDump.swift` and tests for shifted alignment, context resets, dtype/shape, hashes and recovery. Verify no-MTP teacher output plus hidden equality on tiny fixtures before generating a pilot. Do not train or measure GPU while the current benchmark is live.
