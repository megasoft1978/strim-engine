# Speculative (MTP) decoding inside the batch: phase 1 measurement (2026-10-26)

Tool: `strim benchbatchverify <model> <ctx> <B> [reps]` (Sources/StrimCLI/Cmd_BatchVerify.swift).
Prefills B sequences, then times a full 64-layer pass feeding S tokens per sequence through the
existing batched path (`DecoderLayer.forwardBatched`: per-sequence AttentionCache, stacked GDN
state). S=1..5 interleaved per round, 6 rounds, median. Model qwen38-4bit, GPU under
`lockf /tmp/strim-bench.lock`, background load avg 3-4 (other processes; absolute ms +-5%).
Verify cost only: no draft, no rollback, no sampling.

## Implied aggregate speedup over plain batched decode (B / ms(S=1))

Bound = E[tok/pass] * ms(S=1) / ms(S). Optimistic: ignores draft (~2-6 ms/pass), reseed and
rollback. E: prose 1.51 at S=2, 2.0 at S=3 (accept ~51%); code 3.76 at S=4 (accept 94%).
Plain batched aggregate: B=2 47 tok/s (23.7/seq), B=3 61 (20.3/seq), B=4 71.5 (17.9/seq), 1K ctx.

| B | prose S=2 | prose S=3 | code S=4 |

| 2 | 1.25x | 1.20x | 1.90x |
| 3 | 1.03x | 1.06x | 1.55x |

## Verdict

Kill criterion (< 1.3x on both prompt types at B=2 and B=4): not met by the letter, because code
reaches 1.9x / 1.57x. But prose, the common agent case, is <= 1.25x at B=2 and <= 1.0x at B=4, and
the code figures are an upper bound before draft cost. Net: **NO-GO for a general BatchSpec as
the current kernels stand; phase 2 not started.** Per-request decode at B=4 stays ~18 tok/s,
which is the plain-batch number; spec in-batch cannot reach rapid-mlx's 24 tok/s per request
on prose.

## Why the cost curve is steep (and what could move it)

The verify pass is not weight-bandwidth bound beyond S=1. Extra cost per added token:
B=1 ~3-4 ms, B=2 ~10-14, B=4 ~25-35. Two causes:

1. GDN recurrence for B>1 uses the compiled tensor recurrence (`GDN.recurrenceNoStateMMFn`);
   the Metal kernel `GDNMetal.run` is B=1 only (grid has no batch dim, GDN.swift:317).
2. M = B*S quantized matmuls fall off the M=1 fast path (SWIFT-NEXT: 114-253 vs 240-451 GB/s).

Experiment (not committed, GDN.swift is outside this slice): for B>1 and S<=8, loop
`GDNMetal.run` per sequence over slices of q,k,v,g,beta,ssm and concatenate. Measured 1K ctx:

| B | S=1 | S=2 | S=3 | S=4 | S=5 |
|--:|--:|--:|--:|--:|--:|
| 2 | 43.8 (was 43.5) | 48.0 (52.3) | 63.7 (71.4) | 73.8 (84.8) | 84.1 (97.7) |
| 4 | 52.1 (was 56.9) | 77.1 (86.9) | 104.2 (122.4) | 105.4 (130.9) | 108.8 (140.1) |

Side finding: this makes **plain** batched decode at B=4 about 8% faster (56.9 -> 52.1 ms) with
no spec at all; recommend landing it independently (needs checkbatchparity, since arithmetic
moves from the tensor recurrence toward the B=1 kernel, likely closer to B=1 output).
With it the bounds become: B=2 prose S=3 1.37x, code S=4 2.2x; B=4 prose S=3 1.0x, code S=4 1.86x.
B=4 prose still gains nothing: the M=B*S matmul cost dominates, which needs a qmm change.

## Recommendation

- Drop in-batch MTP for B>=3 and for prose workloads.
- Land the per-sequence GDNMetal.run loop for B>1 (plain batch speedup, small, independent).
- If revisited, scope to B=2 with a multi-sequence recording GDN kernel (batch dim in the grid,
  `recordStack`), depth = min over sequences of adaptive depth, per-sequence GDN rollback from
  stacked history (extra state = S * 3 MB fp32 ssm per GDN layer per sequence, 48 layers: ~144 MB
  per sequence per token of depth) and KV rollback by offset. Expected gain only ~1.2-1.4x on
  prose at B=2, up to ~2x on code.
- Alternative for the h2h gap: improve plain batched per-seq rate (qmm for M=B, per-seq GDN
  kernel) rather than speculation.

## Risks if phase 2 is pursued

- Batched qmm tiling drifts logits (0.15-0.45), near-tie flips vs B=1 SpecStream output: gate
  with checkbatchparity and report top1-top2 margins at mismatches.
- AttentionCache.offset is `private(set)`: rollback needs a truncate API in Cache.swift.
- Mixed depth/priority: sequences joining a spec batch need MTP head state seeded from prefill.
