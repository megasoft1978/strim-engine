# DeepSeek V1 — engine/harness baseline, design, protocol (2026-10-26)

This is the audit the brief asked for, run against the repository in
the repository root. It is deliberately explicit about what is
measured, what is inferred, and what is **not** comparable.

## 0. Target: which engine is this?

There are two different projects in play.

| | this repository | Molten |
|---|---|---|
| code | Swift + MLX (`Sources/StrimCore`) | Rust + Metal ([zhangshuibai/molten](https://github.com/zhangshuibai/molten)) |
| model | **Qwen3.8-27B dense**, affine 4-bit, group 64 | **LiquidAI LFM2.5-24B-A2B**, MoE with 2B active, MLX 4-bit |
| hardware | M5 Max 64 GB | M5 Max 128 GB in its published run |
| concurrency | MTP speculative; product path batches via rapid-mlx | one sequence, queued |
| headline | 41–50 tok/s (dense 27B) | 305 tok/s decode at 256 ctx, 285 at 4K |

Molten is **not** the engine in this repository and **not** a 27B dense model. Its 300+ tok/s is
mostly the model (2B active parameters per token, ~1 GB of active weights) rather than a kernel
win over a dense 27B. It is useful as a same-machine reference for kernel design, not as a
like-for-like score. The brief's "27B 4-bit" matches this repository; everything below is
therefore about `strim-engine`. If the intended target was Molten, stop here and re-baseline in
that repository — the numbers, model and bottlenecks are different.

"Molten may be the engine/reference name": verified, it is a **reference**, not this engine.

### 1.3 Engines in the repository

There are two paths, and they must not be mixed:

1. **Swift engine** — `Sources/StrimCore`, the parity/ownership implementation. Default now:
   fused GDN recurrence kernel, fused gate+up MLP, MTP depth 2, fused conv+silu, causal-mask
   prefill. `STRIM_GDN_TENSOR=1` restores the MLX-op/TF32 reference path.
2. **Product** — `strimd` (FastAPI router) serving **rapid-mlx**: speed mode `Qwen3.6-35B-A3B`
   ～127 tok/s, quality mode `Qwen3.8-27B` 4-bit + MTP ～48.2 tok/s (docs/SWIFT-PERF.md). The
   Swift engine is not the shipping backend.

### 1.5 Bottleneck diagnosis

1. **Decode is the weight stream.** A depth-2 pass streams ~12.6 GB. At 50.3 tok/s and 1.92
   tok/pass that is ~26 passes/s ≈ **330 GB/s** against a measured ~530 GB/s ceiling. MTP raises
   tok/s only by raising tokens/pass; the bytes per pass are fixed. No kernel rewrite changes
   the 12.6 GB.
2. **MTP head and acceptance.** Two 389 MB `lm_head` calls per round plus the head layer;
   acceptance is 52% on natural prose but 91% on code. The head + bookkeeping is ~4–8 ms/pass.
   Removing syncs is worth ~0.5–1%; the dependent `lm_head` work is not removable by scheduling.
3. **Prefill is compute-bound at the qmm roofline.** At S=1024: MLP 63%, GDN 30%, attention 9%.
   MLX's large-M 4-bit qmm measures 38–55 TFLOP/s; 54 GFLOP/token gives a **~890 tok/s
   roofline**. 780–870 is 88–98% of it. 1,200 needs >65 TFLOP/s effective, not a scheduling fix.
4. **Harness fixed cost is mostly the agent, not the MCP.** Our 9 MCP tools are 582 Qwen tokens.
   The external agent's own system prompt and tools dominate (aictrl measured Codex at 4,047
   system + 3,614 tool tokens per call; Pi at 2,601 + 1,609; their counts use `o200k_base`, ours
   the Qwen tokenizer, so compare shape not exact numbers). Optimising the MCP surface further
   buys little.
5. **Concurrency is admission-level, not preemptive.** `strimd` has per-backend gates (speed 4,
   quality 2, background 1) and now admits before the upstream call, but a request already in
   rapid-mlx's batch cannot be preempted. The Swift engine itself has no server, batching or KV
   paging.
6. **KV is bfloat16**, 16 full-attention layers, 4 KV heads; ~268 MB at 4K. Decode is
   weight-bound at short context, so FP8/int8 KV is a long-context/memory lever, not a
   short-context speed lever.

### 1.6 Missing facts (not invented)

- **Target repo confirmation.** Current evidence says this repository; Molten is a different
  model/engine. Ask before moving the work.
- **Daily agent harness.** We measured the MCP surface, not the CLI's system prompt, tool set or
  compaction. Codex, Claude Code and Pi have different fixed costs and different tool support.
- **Model source revision.** Local files are hashed above; the Hugging Face revision they came
  from is not recorded.
- **Quiet-machine runs.** The UTM VM and Chrome were running. The brief's protocol should state

## 4. Reproducible A/B protocol

**Model and files.** Record `config.json`, `model.safetensors.index.json` and every shard's
SHA-256 (values in §1.1). Quantisation is affine 4-bit, group 64; MTP head separately hashed.
A run without these hashes is not comparable.

**Hardware/software.** Record `sw_vers`, `sysctl machdep.cpu.brand_string hw.memsize`, `uptime`,
`pmset -g therm`, `git rev-parse HEAD`, `swift --version`, the `mlx-swift` pin, and the
`rapid-mlx` version. Confirm no process is listening on 8201/8202 (a loaded product backend
inflates a 38 ms pass to 214 ms; documented in `docs/SWIFT-NEXT.md`).

**Prompts.** [bench/ab_prompts.json](../bench/ab_prompts.json): 8 prompts (natural, code, sql,
rust, csvpy, prose, math, json), tokenized with `models/qwen38-4bit/tokenizer.json`; expected
lengths 59/93/33/29/26/51/41/30. Greedy (`temperature=0`), max 64 new tokens, depth 0 and 2.
Prefill: synthetic chunk of 1024 and 4096 tokens, cold cache.

**Warmups/repeats.** Two warmups, then 5 repetitions. For path A/B use the in-process
alternating instrument (`strim benchpathspec`, `strim benchpathS`); for cross-build A/B alternate
the process order and report min, median and CV. Never compare a single sample per arm.

**Metrics.** TTFT (prefill ms + first token), prefill tok/s, decode tok/s, tokens/pass, draft
acceptance, ms/pass, end-to-end task wall time, tokens in/out (Qwen tokenizer), USD at the
current provider price, and quality/exactness. Report raw logs, not only a summary.

**Quality gates, in order.** (1) `strim gen … 16` matches the Python reference token for token;
(2) `benchspec … 0` EXACT; (3) 8-prompt corpus `EXACT` not below the current 7/8; (4) tool-call
tokenizer/template round-trip; (5) optional MATH-500/IFEval if a change can affect quality.
A speed win that fails (1)–(3) is rejected, not documented as a win.

**Concurrency.** 1/2/4/8 requests, distinct prompts, per-request and aggregate tok/s, priority
slot waits from `/v1/strim/status`; same model and context per arm.

**Harness.** Separate from kernel throughput: same CLI version, same system/tool configuration,
a 50-read tool trace, a short task and a long task; measure turns, tool calls, harness time per
turn, input/output tokens and task success. Do not mix harness numbers with engine tok/s.

**Script.** [scripts/ab_bench.sh](../scripts/ab_bench.sh) records the environment, hashes
(optional `HASH=1`), tokenizes the prompts, runs prefill 1K/4K, depth 0/2, the interleaved path
A/B and `gen 16`; `QUICK=1` skips the corpus/tests. Raw output lands in
`bench/results/ab-<timestamp>/`. The validated quick run is
[ab-20261026-073925](../bench/results/ab-20261026-073925/).

## 5. First iteration — one change at a time

Two experiments were run after the baseline. Both were measured against the same build and
prompts.

**Rejected: 2D flatten of the prefill qmm.** MLX's 3D `[1,S,K]` path can be flattened to
`[S,K]`; isolated `benchqmmM` showed 1.14× on gate+up and 1.17× on qkv at M=1024. End to end it
was **not** a win: 1024 tok/s 822 (2D) vs 824 (3D); 4096 763 vs 774. The reshape/copy and the
different GEMM tiling cancel the isolated gain. Reverted, no flag left behind.

**Kept: MLX's causal mask for offset-0 prefill.** A fresh prefill has `offset == 0`, so the S×S
f32 mask array built in Swift (8M assignments/layer at S=1024) is exactly the standard causal
mask. `MLXFast.ScaledDotProductAttentionMaskMode.causal` is bit-identical (`logithash` over 8
positions matched) and faster:

| S | manual mask | causal | delta |
|--:|---:|---:|---:|
| 1024 | 1.27 s | **1.21 s** | −5% |
| 4096 | 5.22 s | **5.05 s** | −3% |

Gates after the change: `gen 16` matches the reference, depth-0 EXACT (91), depth-2 natural
EXACT (107). Commit `1923ee4`; source in [Attention.swift](../Sources/StrimCore/Attention.swift).
Cached/verify passes still build the manual offset mask, so speculative attention is unchanged.

The raw quick run after the change is
[bench/results/ab-20261026-073925](../bench/results/ab-20261026-073925/): kernel 49.9 vs tensor
62.7 ms/pass at depth 2 (−20.3%), cross-path outputs identical, `gen 16` matches.

### Adaptive MTP depth — kept

Depth 2 was tuned for 46% prose acceptance; code prompts accept 91–94%, where a third draft
pays. The controller keeps an EWMA of accepted drafts, climbs 2 → 3 after four rounds above
0.82, falls back below 0.60, and never goes to 1 (depth 1 lost on every measured prompt).

| prompt | fixed depth 2 | adaptive | delta |
|---|---:|---:|---:|
| mean, 8 prompts | 49.2 tok/s | **52.9** | **+7.4%** |
| code | 53.1 | **59.1** | +11.3% |
| json | 50.4 | **58.1** | +15.3% |
| sql | 54.2 | **59.3** | +9.4% |
| math | 54.0 | **58.7** | +8.7% |
| natural | 41.0 | 40.3 | −1.7% (noise; stays at 2) |
| prose | 36.8 | 37.9 | +3.0% |

Both are 7/8 EXACT (prose shared MISMATCH); `gen 16` and depth-0 EXACT pass. The mechanism is
tokens/pass (code 2.87 → 3.53) at ~7% more pass time, not a faster pass. Default now adaptive;
`STRIM_MTP_FIXED=1` restores fixed depth 2. This was measured on a loaded machine; the quiet
corpus A/B remains on the list.

### Harness/MCP — the tool surface is not the overhead

Our MCP surface is 9 tools / **582 Qwen tokens**; the agent's own fixed cost dominates (aictrl
measured Codex at 4,047 system + 3,614 tool tokens, Pi at 2,601 + 1,609, on their tokenizer).
Shrinking the MCP further buys little; the lever is the agent's prompt/turn count.

One real bug was fixed: `strimd.delegate` (the MCP tool implementation) posted straight to the
backend, bypassing `PriorityGate`, so a batch of MCP calls could occupy the backend while a
chat request waited — the same class as the earlier chat-relay ordering bug. It now holds the
per-backend interactive slot for the whole call; `bench/test_mcp_gate.py` is the regression
test. This is admission control, not mid-token preemption: a request already in rapid-mlx's
batch cannot be preempted. Async compaction is not in this repository; it belongs to the agent
harness that formats the context (Codex/Claude Code), not to the MCP tool layer.

The tool-call bridge now has a regression test (`bench/test_tool_bridge.py`): Anthropic
`tool_use`/`tool_result` ↔ OpenAI `tool_calls`, string **and dict** arguments, and the four
Qwen special tokens (`<tool_call>` 248058, `</tool_call>` 248059, `<tool_response>` 248066,
`</tool_response>` 248067). It caught a real robustness gap: `_anthropic_message` only
accepted string `arguments`; a dict raised `TypeError`. Fixed in `strimd.py`. What is still
missing is an end-to-end run with a real tool trace and a live backend.

## 6. Smallest high-impact next sequence

1. **Adaptive MTP depth (P2) is done** — default, gated on the 8-prompt corpus; a quiet-machine
   run should confirm the +7.4%.
2. **Tool-call bridge (P3).** Build one real tool-call trace: OpenAI `tool_calls` → Qwen chat
   template → backend → parse. The special tokens already round-trip; this tests the whole
   path, which is where coding agents actually fail.
3. **Long-context KV measurement (P4).** At 8K/16K compare bf16 vs FP8/int8 on memory, decode
   tok/s and quality. Do not implement until the measurement shows a net win.
4. **Harness comparison (P6).** Once the daily harness is confirmed, run Pi vs that harness on
   the same MCP and the same tasks; count tokens and task success, not just overhead.

## 7. What I need confirmed
