# Quality tasks — three complex, checker-backed coding tasks

**Date:** 2026-10-25 · **Source:** history-derived and synthetic packages in
an earlier private lab checkout (`STRIM_TASK_LAB`, not part of this repository) · **Runner:** `run_task.py` (removed 2026-10-27; replaced by `strim agentbench`)
(mini-SWE-agent + local OpenAI endpoint + the package's own `verify.sh`)

The point is quality, not speed: each task has a deterministic checker that fails at the base commit
and passes at the fix, and the hidden tests are only copied in at verification time.

---

## The three tasks

| # | Task | Language | Why it is a good quality probe | Checker |
|---|---|---|---|---|
| 1 | `debug-flaky-concurrency` | Python | A real race-condition hunt in an ordered thread pool: out-of-order delivery, overlapping callbacks, lost jobs. Fix must survive 20 stress runs, not one. | visible tests + 20× hidden stress |
| 2 | `feature-multifile-edgecases` | Python | Add `slug` across model, store, persistence, search, CSV import, reports and CLI; must keep old catalog files loading and follow existing conventions. Tests breadth + consistency. | hidden unit + CLI tests |
| 3 | `spec-from-tests` | Python | Implement `durations.humanize()` from conventions, existing tests and docs — edge values, invalid input, formatting. Tests inference and taste, not just coding. | hidden unit tests |

All three are self-contained Python packages (no network, no node_modules), so they run offline and
the result is reproducible. `linked-recipe-macros` (TypeScript, real Traqly domain logic) stays as a
fourth, heavier task for later.

### Exact prompts

The model-visible prompt is the package's `issue.md` verbatim, with the working directory set to a
fresh copy of the repository at the base commit. No plan, no hidden tests, no fix commit. Example
(task 1):

> Intermittent production bug in `orderedpool`: under load, results are sometimes delivered to
> `on_result` out of submit order, occasionally two callbacks run at the same time, and now and then
> a job is lost so `pool.wait()` never returns. It only shows up with several producer threads and
> slow callbacks; single-threaded tests are green. Find every root cause and fix it. Keep the public
> API … and the guarantees in the docstrings unchanged. The result must be correct on every run,
> not just most runs.

### Protocol

- Agent: mini-SWE-agent, `step_limit` 12–20, temperature 0.2, seed 0, 3000 max tokens per step.
- Environment: local shell in the staged clone, 120 s per command.
- Verification: the package's `verify.sh` runs after the agent exits; hidden tests are injected then.
- One model per run; no other GPU work; record model, quant, server, steps, wall time, diff size.
- Scoring: PASS/FAIL from `verify.sh`; secondary metrics are steps used, wall time, lines changed,
  and whether the patch compiles/tests before the hidden suite.

## First result (2026-10-25): 8-bit, 12 steps

| Field | Value |
|---|---|
| Model | Qwen3.8-27B, MLX 8-bit, no MTP, rapid-mlx server |
| Task | `debug-flaky-concurrency` |
| Agent | mini-SWE-agent, 12 steps, 273 s |
| Patch | 19 added / 7 removed across `orderedpool/pool.py` and `sink.py` |
| Visible tests | 3/3 pass |
| Hidden stress | **FAIL — out of order, 1 of 20 runs** |
| Verdict | **FAIL** |

Reading: the model understood the shape of the bug (it rewrote the pending/emit path and added a
lock), but did not find the ordering root cause, and it ran out of steps (`LimitsExceeded`) before
re-testing under stress. That is a useful quality signal: it separates "looks like a fix" from "is
correct under concurrency", which is exactly what a local coding agent must be judged on.

### Results so far

| Task | 8-bit | 6-bit | 4-bit |
|---|---|---|---|
| `debug-flaky-concurrency` | FAIL (273 s) | FAIL (281 s) | not run |
| `spec-from-tests` | not run | **PASS** (31 tests, 558 s) | **PASS** (30 tests, 211 s) |
| `feature-multifile-edgecases` | not run | not run | not run |

Both models patch the concurrency task in the same way and both miss the ordering root cause, so the
task does not separate 8-bit from 6-bit at 12 steps. `spec-from-tests` passes on both, at 2.6× the
wall time on 6-bit (the decode difference). The 4-bit concurrency run is the next discriminator; if
it also fails, the task needs more steps or a stronger model, not a different quant.

## What is measured next

1. Run all three tasks on 8-bit (baseline) — 3 runs each, pass rate.
2. Repeat on 6-bit graded, 5-bit, 4-bit, oQ4e-mtp — same prompts and steps.
3. Record steps-to-pass and wall time; a model that passes in 8 steps is better than one that needs 20.
4. Only then tune the harness (step limit, prompt, retry policy) — otherwise harness changes hide
   model differences.

## TypeScript / React suite (requested 2026-10-25)

Three history-derived Traqly tasks, all real React/TypeScript code (`apps/chef`), run with the same
harness: mini-SWE-agent, 20 steps, rapid-mlx serving **Qwen3.8-27B 4-bit**, hidden Vitest tests
injected only at verification time. No test file is visible or editable in the clone.

| Task | What it exercises | Result | Tests | Wall | Patch |
|---|---|---|---:|---:|---|
| `canonical-merged-ingredient-names` | React line rendering, merged-ingredient naming | **PASS** | 2/2 | 227 s | 3 files, +10/−2 |
| `import-prep-note-text` | import payload text semantics, duplicate prep notes | **PASS** | 5/5 | 326 s | 1 file, +6/−2 |
| `linked-recipe-macros` | nutrition aggregation, panel wiring, docs | **PASS** | 4/4 | 254 s | 3 files, +16/−11 |

**3/3 on 4-bit.** The diffs are in the components and library (`recipe-macros.ts`, `ingredient-line-row.tsx`,
`ingredient-line-payload.ts`, `recipe-macros-panel.tsx`); no test file was modified. This is the first
evidence that the 4-bit speed leader (51 tok/s) also holds coding quality on React/TypeScript tasks,
including the `linked-recipe-macros` task that previously scored 0/6 in a different harness/quant.

Repeat on the hardest task: 4-bit **3/3 PASS** (254 s, 393 s, 416 s), 8-bit **1/1 PASS** (280 s).
Total TypeScript evidence: **5/5 PASS on 4-bit**, 1/1 on 8-bit.

Caveat: three tasks, one repo, 20 steps. It is a strong signal, not a pass rate. The next step is
to repeat each task 3× and add a fourth task from a different repo to avoid overfitting to Traqly.
