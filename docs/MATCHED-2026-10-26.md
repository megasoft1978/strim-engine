# Matched same-day decode: Swift engine vs rapid-mlx (2026-10-26)

Same machine (M5 Max 64 GB, UTM VM + Chrome resident), same eight prompt texts from
`bench/ab_prompts.json`, 64 generated tokens, greedy, one request at a time.

- **Swift**: `strim benchspec models/qwen38-4bit models/qwen38-mtp-4bit 64 2 <ids>`;
  end-to-end tok/s and the new decode-only rate (`emitted / (seconds - prefillSeconds)`).
- **rapid-mlx**: `strimd` quality mode (`strim-quality` → rapid-mlx, MTP on), HTTP streaming
  with `stream_options.include_usage`; TTFT = first content delta, decode = completion
  tokens / (total - TTFT).

| prompt | Swift end-to-end | Swift decode | rapid-mlx decode | rapid-mlx end-to-end |
|---|---:|---:|---:|---:|
| natural | 41.3 | 41.4 | 46.3 | 33.7 |
| code | 60.8 | 61.5 | 47.7 | 42.4 |
| sql | 58.8 | 59.0 | 50.4 | 41.6 |
| rust | 56.8 | 57.0 | 52.3 | 42.1 |
| csvpy | 54.6 | 54.8 | 50.5 | 41.8 |
| prose | 37.4 | 37.5 | 45.3 | 38.1 |
| math | 59.8 | 60.1 | 51.8 | 42.7 |
| json | 59.3 | 59.5 | 52.0 | 42.7 |
| **mean** | **53.6** | **53.8** | **49.5** | **40.6** |

Rapid-mlx mean TTFT was 0.29 s on these short prompts. Swift prefill is measured
separately by `benchprefill` (cold-cache 4K: 825–846 tok/s); these short-prompt TTFTs are
not a 4K prefill comparison.

Caveats: the engines tokenize/template the prompts differently (rapid-mlx prompt tokens
38–104), so this is a matched **text/task** comparison, not a token-identical one. The
runs were same-day but not interleaved; the machine load was similar (load average ~6).
On this run the Swift engine is **~8% faster in decode-only** and **~32% faster
end-to-end** than rapid-mlx, and clears the objective's `>48.2 matched rapid-mlx` decode
bar. The matched run above predates the adaptive depth-4 climb; the subsequent corpus is **55.1 decode-only / 54.9 end-to-end**, so the >55 decode target is met only on the decode-only metric, not end-to-end.

The oQ4e checkpoint was not part of this run; its download remains incomplete.
